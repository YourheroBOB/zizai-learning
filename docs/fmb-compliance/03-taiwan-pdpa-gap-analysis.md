# 台灣個資法一般要求：缺口與建議

## 適用說明

以下按個資法一般原則整理，供工程與營運盤點，不構成法律意見。個資法是否及如何適用，須由營運者依實際身分、資料用途、使用者關係、部署與服務提供方式判定。應核對正式法規及適用版本，必要時由熟悉台灣個資法的法律顧問審閱。

## 一般要求與本專案初步對照

## 建議最小告知內容

由實際資料控制者依服務情況完成，不宜直接照抄本範本而不確認：

- 誰在處理資料，以及負責聯絡的窗口。
- 各功能處理的目的與資料類別；明確區分本機學習狀態、使用者匯出與主動回報。
- 回報會送到哪個服務／接收者、哪些欄位會送出，以及是否會一併處理請求中繼資料。
- 個資利用的期間、地區、對象及方式；如使用外部服務，說明適用的資料流。
- 使用者可行使的權利及受理方式。
- 拒絕提供非必要資料的影響；不勾選回報時應維持本機使用方式。
- 本機資料如何清除、匯出檔案由誰管理，以及回報資料如何申請刪除。

## 優先改善清單

### P0：確認責任與外部處理

1. 指定網站／回報 API 的資料控制者及聯絡窗口。
2. 由 API 維護者確認完整 payload、日誌、存取權限、服務所在地、保存期限、備份及刪除方法。
3. 由 BOB 決定授權不明生字清單的發布範圍與程式碼授權策略（詳見 `01-license-inventory.md`）。

### P1：降低蒐集與外洩風險

1. 不把可識別資料放進自由文字備註；在備註欄旁提示避免輸入姓名、聯絡資訊、帳號或其他非必要資訊。
2. 回報採資料最小化；檢視是否可不送備註、頁面或其他非必要欄位。
3. 檢查前端、API、主機及錯誤監控是否記錄 request body、localStorage 或完整例外物件。
4. 確認 Google Fonts、主機及外部連結可能產生的請求中繼資料，並納入告知與服務選擇。

### P2：完善使用者控制

1. 提供本機資料清除功能及資料保管說明。
2. 在匯出前提示匯出資料可能包含使用者輸入的備註及學習脈絡。
3. 建立外部回報資料的查詢、更正、停止利用及刪除受理流程。
4. 完成後以實際程式碼、瀏覽器網路檢查與 API 設定覆核文件，並定期更新。
